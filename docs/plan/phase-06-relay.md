# Phase 6 — 인터넷 접속용 랑데부 + 릴레이

## 목표

서로 다른 NAT 뒤의 기기도 AnyDesk처럼 "ID + 비밀번호"로 접속할 수 있게 한다. 사용자가 직접
운영하는 릴레이 서버를 쓰며, 릴레이는 암호화된 패킷만 전달하고 평문을 볼 수 없다.

## 설계

- `open-desk-relay` 서버 바이너리
  - 랑데부: 호스트는 릴레이에 QUIC 제어 연결을 유지하고 인증서 지문으로 등록한다.
    릴레이는 지문마다 9자리 숫자 ID를 발급·영속화한다(지문 소유는 TLS 클라이언트 인증서로 증명).
  - 접속 요청: 뷰어가 ID로 접속을 요청하면 릴레이는 UDP 포트 한 쌍(호스트용/뷰어용)을
    할당해 양측에 알린다. 각 측은 할당받은 포트로 토큰 패킷을 보내 자기 주소를 등록하고,
    이후 릴레이는 두 주소 사이의 UDP 패킷을 그대로 전달한다(TURN과 유사).
  - 그 위에서 뷰어와 호스트는 기존과 똑같은 QUIC + SPAKE2 세션을 종단 간으로 맺는다.
    따라서 릴레이를 신뢰하지 않아도 기밀성·인증이 유지된다.
  - 남용 방지: 할당 수·대역폭·유휴 시간 제한, 할당 토큰은 추측 불가능한 난수, 요청 속도 제한.
- 클라이언트: 설정에 릴레이 주소 입력. 홈 화면에 "내 ID" 표시, 접속 입력란은 IP 주소와 ID를 모두 허용.
- 릴레이 실행은 단일 바이너리 + 설정 파일, Docker 이미지 예시 제공.

## 작업 항목

- `crates/relay` 서버, `crates/net`의 릴레이 클라이언트, UI 연동
- 테스트: 로컬 릴레이를 통한 E2E 세션, 잘못된 토큰 패킷 무시, 할당 만료, ID 영속화

## 완료 조건

- 릴레이 경유 E2E 테스트 통과, 로컬 릴레이로 두 기기 간 접속 수동 확인

## 구현 노트

- 릴레이는 UDP 포트 쌍을 할당하고, 각 쪽이 `ODRB || 토큰` 데이터그램으로 주소를 등록하면 그 두 주소
  사이의 데이터그램만 그대로 전달한다. 바인딩 데이터그램이 유실되면 호스트 쪽이 영영 패킷을 못 받으므로,
  릴레이는 `ODRA || 토큰`으로 확인 응답을 보내고 클라이언트는 확인될 때까지 재전송한다.
- 등록 시 호스트는 기기 인증서를 TLS 클라이언트 인증서로 제시하고, 릴레이는 서명 검증(키 소유 증명) 후
  지문으로 ID를 찾는다. 뷰어는 인증서 없이 접속 요청만 한다. 릴레이 자체 인증서는 검증하지 않는다(릴레이를
  신뢰하지 않는 설계이며, 가짜 릴레이가 할 수 있는 일은 연결 방해뿐이다).
- 호스트의 릴레이 경유 접속은 `RelayedAcceptor`로 기존 `HostEndpoint`의 인증 경로(`handle_incoming`)를
  그대로 타므로 비밀번호, 시도 제한, 단일 세션, 승인 정책이 동일하게 적용된다. 단, 시도 제한은 출발지 IP 기준이라
  릴레이 경유 시도는 모두 릴레이 IP로 집계된다(남용 시 릴레이 경유 접속만 잠깐 막힘).
- 호스트 서비스는 릴레이 등록이 끊기면 2초→60초 지수 백오프로 재등록하고 `HostEvent::Relay`로 상태를 알린다.
- 릴레이 남용 방지: 출발지 IP당 분당 30건, 호스트당 대기 접속 4건, 전체 할당 상한, 바인딩 30초·유휴 120초 만료.
- 테스트: 릴레이 단위(포워더: 제3자 주입/위조 바인딩 무시, 할당 상한, ID 영속), 릴레이 E2E(ID 접속, 틀린 비밀번호는
  호스트가 거부, 없는 ID, 재시작 후 같은 ID), 세션 E2E(호스트 서비스 등록 → 뷰어가 ID로 접속해 프레임 수신),
  GUI E2E(접속 폼에 9자리 ID 입력 → 릴레이 경유 → 승인 → 세션 성립).
- 운영 문서: [docs/relay.md](../relay.md).
